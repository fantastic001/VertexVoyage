**Question.** As the streamed graph grows buffer by buffer, how many vertices
does the partitioner move (repartition) per buffer, and how does that volume
depend on $P$, $RF$ and $\mu$? Repartitioning is the cost side of the
balance/quality trade-off in [balance-penalty sensitivity](../E04-balance-penalty/README.md).

# How it was run

`vv temporal_test` runs on CITESEER ($\mu=1$) and AstroPh ($\mu \in \{0.5, 1\}$),
`neighbors.all` partitioner, sweeping $P \in \{2, 4, 8\}$ and $RF \in \{1, 2, 4\}$.
Each row below is the per-buffer count of repartitioned vertices for one
$(P, RF)$ configuration (the notebook also reports it as
`repartitioning percentage` = moved / total vertices). Analysis:
[`notebooks/analyze_results.ipynb`](../../notebooks/analyze_results.ipynb).

# Conclusion

- Repartitioning volume **grows with $P$**: more partitions means more
  boundary vertices whose best assignment flips as neighbours arrive.
- It **grows with $\mu$**: a stronger balance penalty forces reassignments
  purely to equalise sizes (visible comparing AstroPh $\mu=0.5$ vs $\mu=1$).
- $RF$ inflates the counts — with replication factor $r$ each logical move
  touches multiple physical copies (CITESEER $P=8$, early buffers:
  $RF{=}1 \to [0, 228, 366, \dots]$ vs $RF{=}2 \to [0, 456, 732, \dots]$).
- The first one or two buffers show near-zero moves (cold start, everything
  is "new"), then the per-buffer count stabilises around a graph-dependent
  band.
